# 金字塔表达工作室

一个入口，按任务选用写作、分析、演示或审稿流程。默认沿用用户的语言和目标，直接交付请求的成稿、提纲或诊断；不把每次任务变成方法课。

## 先识别任务

从现有上下文识别读者、读者要回答的问题、已有材料、交付形式及长度。能合理判断就继续；只有缺失信息会改变核心答案时才提问。用户只要提纲时不扩写正文，只要审稿时不擅自全文重写。分析任务没有证据结论时，交付问题界定与验证计划，不强造塔尖。

按需读取，勿一次加载整套资料：

| 请求 | 读取 | 交付 |
|---|---|---|
| 邮件、周报、摘要、短说明 | [workflows.md](references/workflows.md) 的短文部分 | 可直接使用的短文 |
| 报告、建议书、文章框架或长文 | 同文件的长文部分 | 所需深度的提纲或全文 |
| PPT、路演、汇报故事线 | 同文件的演示部分 | 页标题、支撑证据、图示建议、讲稿要点 |
| 找逻辑问题、检查原稿 | [audit.md](references/audit.md) | 有原文依据的诊断与修正建议 |
| 原因诊断、方案比较、问题树 | [analysis.md](references/analysis.md) | 界定问题、假设、验证办法、条件性建议 |
| 数据或来源影响结论、仅使用给定事实 | [evidence.md](references/evidence.md) | 保留事实边界的结果；需要时附核对记录 |
| 解释或学习金字塔原理 | [learning-map.md](references/learning-map.md) | 针对问题的讲解与练习 |

混合任务可组合流程；来源核对贯穿写前和写后，不需要安装其他 skill 或启动其他代理。

## 统一结构规则

1. **先回答读者问题。** 用具体判断、建议或事实概括开场；只有理解答案必需的背景才前置。SCQA 供需要铺垫的场景使用，不强制每封邮件四段。
2. **上层概括下层。** 下层分别回答“为什么”“如何”“凭什么”；“现状分析”“几点建议”只是主题标签，不能充当实际结论。
3. **同层回答同一个问题、承担同一种角色。** 先找共同父问题及角色，再判断是否混组；不同主题可以共同构成原因或风险。
4. **分组有边界，排序有依据。** 检查重复，只有范围明确才能判断穷尽；不知道完整范围时说明无法确认。时间、结构、程度、演绎顺序按材料选择；不硬凑三点、固定层数或固定页数。
5. **归纳与演绎不混层。** 归纳成员共同支持概括；演绎各步相依。建议可先表达，推导与证据下沉。分类并不能证明因果关系。
6. **保留事实力度。** 不为了让结构完整而补事实、数字、承诺、责任人、截止时间或效果；不把相关写成因果，把计划写成成果。
7. **表达具体。** 用清楚的主语、动作和结果，每句承担一个主要判断；关键术语上下层保持一致。标题尽可能表达观点，但证据不足时用问题式标题，不伪装成已证实结论。
8. **交付符合请求。** 自查留在内部；方法标签、思考过程、评分表仅在用户要求教学或审稿时显示。没有发现问题就允许原文通过。

## 参考资料的优先级

本文件及 workflows、audit、analysis、evidence 是整合后的操作规范。其他文件是原资料的学习与例子库，出现冲突时以这五份文件为准。特别是旧资料中的固定三点、固定词数、图表90%等，不作为合格门槛；案例及未核对的统计不作为任务证据。原书页码只能作为来源包的定位线索，参见 [source-anchors.md](references/source-anchors.md)，不得声称本次已核实原书引文。
